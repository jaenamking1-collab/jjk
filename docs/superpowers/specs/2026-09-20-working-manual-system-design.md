# 일하는 방식 매뉴얼 체계 설계

작성일: 2026-09-20 (집 PC)
인터뷰 방식: 인스타 릴스 "AI 위임 루프"(@sdk.kim.builds)의 인터뷰 절차를 따라 사용자에게 8문항을 하나씩 물어 정리했다.

## 왜 만드는가

규칙이 `CLAUDE.md`(167줄)에 적혀 있는데도 같은 실수가 반복된다. 대화 기록에서 사용자가 화를 낸 대목은 전부 같은 세 가지다.

- 확인도 안 하고 단정한다 — "거봐 확인도 안 해보고 없다고 하네"(8/24)
- 내가 할 수 있는 일을 떠넘긴다 — "내가 할 수 있는 일 먼저 확인해보고 요청하라고 했음"(8/27), "GIT 풀 이런 거는 니가 하라고 했잖아 매번"(9/3)
- 한 번 정한 걸 다음 세션이 모른다 — "이 얘기를 몇 번이나 한 거냐"(8/28)

원인은 두 가지다. ① 규칙과 절차가 한 파일에 섞여 있어 묻힌다. ② 규칙이 프로젝트 저장소에만 있어, 다른 프로젝트를 열면 처음부터 다시 시작된다.

## 사용자가 정한 기준 (인터뷰 결과)

1. 문제를 발견하면 **고치고 → 테스트하고 → 문제없으면 중간보고**. 허락을 기다리지 않는다.
2. 검증 깊이는 프로젝트 위험도에 따라 다르다. 포트폴리오처럼 돈이 걸리고 고장 이력이 많은 것은 항목을 중요도별로 나눠 자주 볼 것과 천천히 볼 것을 구분한다. 단순한 앱은 통째로 한 번 돌려보면 끝이다.
3. 점검 주기는 **매번 / 배포 직후 / 매일 첫 세션 / 주간** 4단계.
4. 세션 시작 자동 점검은 **가벼운 것만, 항상**. 이상 없으면 한 줄도 쓰지 않는다. (점검만 하다 토큰을 다 쓰고 남는 게 없는 상황을 만들지 않는다.)
5. **일하는 방식은 전체 공용**, 프로젝트 절차는 각 저장소. 새 프로젝트를 열어도 업무 방식이 리셋되면 안 된다 — 인수인계가 되어야 한다.
6. 새 프로젝트에는 **한 줄 표시 + 자동 설치**. 저장소 `CLAUDE.md` 맨 위에 공용 규칙을 읽으라는 한 줄만 두고, 규칙 본문은 공용 기억 한 곳에서만 고친다.
7. 중간보고는 **두 줄** — 무엇을 고쳤다 / 무엇으로 확인했다.

## 구조

### 공용 기억 저장소 (claude-memory) — 한 장

파일 위치는 공용 기억 저장소 최상위의 `일하는_방식.md`. 두 PC에서는 이 저장소가 각 프로젝트의 기억 폴더로 연결되어 있고, 기억 목록(`MEMORY.md`)은 세션마다 자동으로 읽힌다. 그래서 `MEMORY.md` 맨 위에 이 파일을 가리키는 한 줄을 두면 어느 프로젝트에서 시작하든 자동으로 눈에 들어온다. 원격(웹) 세션은 이 저장소가 붙어 있을 때만 보이므로, 저장소 `CLAUDE.md`의 한 줄 표시가 그 자리를 메운다.

내용 (한 쪽 분량)

- 존댓말. 보고는 두 줄.
- 문제를 보면 고치고, 테스트하고, 보고한다. 허락을 기다리지 않는다.
- 밖으로 나가는 일(배포·공개 페이지·메일)만 먼저 확인받는다.
- 떠넘기기 금지 순서: ① 직접 해본다 ② 막히면 무엇이 왜 막혔는지 근거를 댄다 ③ 사람만 할 수 있는 것만 부탁한다.
- 사용자의 되물음은 점검하라는 신호다. 앞서 한 말을 다시 설명하지 않는다.
- 세션 시작엔 가벼운 점검만. 이상 없으면 말하지 않는다.
- 비밀값은 저장소에 쓰지 않는다. 변경은 항상 커밋·푸시.
- 증거를 못 만들었으면 "됐다"고 쓰지 않는다. 어디까지 확인했고 무엇을 못 했는지 그대로 적는다.

### 각 프로젝트 저장소

- `CLAUDE.md` — 맨 위 한 줄: 공용 `일하는_방식.md`를 먼저 읽어라. 나머지는 그 프로젝트 고유 정보(구조·파일·관례)만 남긴다.
- `.claude/skills/<작업이름>/SKILL.md` — 작업별 절차.
- `.claude/CHECKS.md` — 검증 항목을 4단계로 모은 한 장.
- `tools/INDEX.md` — 재사용 스크립트 목록(툴박스).

### 따라붙게 하는 장치

공용 저장소는 이미 세션 시작 훅이 연결한다. 새 프로젝트에서 `CLAUDE.md` 맨 위 한 줄이 없으면 만들고 시작하도록 그 훅에 한 줄을 더한다.

## jjk의 CHECKS.md 내용

**매번 (내가 만진 것 + 돈 숫자)**
- 바꾼 화면을 실제로 열어 확인, 브라우저 콘솔 오류 0
- 계산을 건드렸으면 PC·모바일 요약 숫자 여섯 개 대조 (같은 식이 두 파일에 따로 있어 어긋나도 보이지 않는다)

**배포 직후**
- `clasp pull`로 원격이 로컬과 같아졌는지
- 트리거 재설치 로그에 15개가 찍히는지 (빠뜨려서 조용히 멈춘 적 세 번)
- 실제 주소로 액션 하나를 호출해 옛 버전이 아닌지

**매일 첫 세션 (가볍게)**
- 안 올라간 커밋
- 분배 데이터가 멈췄는지 (공지창 6시간, 평소 30시간)
- 공개 페이지가 저장소 최신판과 같은지 (미러 누락으로 사용자만 옛 화면을 본 적 네 번)

**주간**
- 6개 운용사 파서 전수 — 빈손이거나 지난달 데이터를 물고 있는지
- 알림로그에 구조 변경 경고가 쌓였는지

## jjk의 작업별 매뉴얼 세 개

**① 백엔드 배포** — 계기: `Code.gs` 변경. 순서: 임시 폴더에서 원격 확인 → `clasp push --force` → 기존 배포 ID로 `deploy` → 트리거 재설치 → 확인. 결정 규칙: `doGet`/`doPost` 경로가 바뀌면 반드시 재배포, 공개 페이지가 쓰는 액션의 응답 형식을 바꾸면 먼저 알린다.

**② 화면 수정·푸시** — 계기: 화면 요청. 순서: 검색으로 위치 찾기 → 수정 → 브라우저 확인 → 커밋·푸시. 결정 규칙: 계산을 건드리면 PC·모바일 둘 다. 공개 페이지와 앱 화면은 일부러 다르다 — 같아야 하는 건 날짜 해석 규칙뿐. 사용자는 웹 주소로 보므로 "pull 하세요"라고 하지 않는다.

**③ 분배금 데이터 점검** — 계기: 주간 점검 또는 숫자·날짜 이상. 순서: 6개사 데이터를 한 번에 받아 빈 곳·지난 회차 확인 → 이상하면 캐시가 아니라 파서를 본다. 결정 규칙: 두 화면이 다르면 렌더가 아니라 데이터를 먼저 의심한다.

세 매뉴얼 모두 끝에 "이 작업에서 과거에 틀렸던 것" 칸을 둔다. 새 사고가 나면 대화에서 고치지 않고 이 칸에 한 줄을 더한다.

## 범위 밖

- 매 턴 규칙을 주입하는 훅, 완료 선언을 막는 훅 — 비용과 소음이 커서 이번에는 넣지 않는다.
- 다른 프로젝트(보건실, 시세 위젯, 회사 일일보고 등)의 작업별 매뉴얼 — 공용 규칙이 자리를 잡은 뒤 그 프로젝트에서 각각 만든다.
