# 일하는 방식 매뉴얼 체계 — 실행 계획

> **작업자용:** 이 계획은 superpowers:subagent-driven-development 또는 superpowers:executing-plans 로 과제 단위로 실행한다. 각 단계는 체크박스로 추적한다.

**목표:** 규칙이 세션·프로젝트를 넘어 살아남게 만든다. 공용 업무 방식 한 장 + 프로젝트별 검증 목록 + 작업별 매뉴얼.

**구조:** 공용 규칙은 공용 기억 저장소(claude-memory) 한 곳, 절차와 검증은 각 프로젝트 저장소. 저장소마다 `CLAUDE.md` 맨 위 한 줄로 공용 규칙을 가리킨다.

**설계 문서:** `docs/superpowers/specs/2026-09-20-working-manual-system-design.md`

## 전체 제약

- 사용자에게 보내는 글은 존댓말. 문서 본문은 기존 저장소 문체(지시문)를 따른다.
- 비밀번호·토큰은 어떤 파일에도 쓰지 않는다. `jjk`는 공개 저장소다.
- 변경은 매번 커밋·푸시한다. 공용 기억 저장소는 비공개이며 별도로 커밋·푸시한다.
- `CLAUDE.md`는 Write로 덮어쓰지 않는다. Edit로만 고치고, 고치기 전에 diff를 사용자에게 보여주고 승인받는다.
- 이 계획에는 테스트 러너가 없다. 각 과제의 "확인" 단계는 실제 명령의 출력으로 증명한다.

**파일**

- 수정: `~/claude-memory/MEMORY.md` (맨 위에 한 줄 추가)

**이 과제가 남기는 것:** 모든 프로젝트에서 세션 시작 시 자동으로 눈에 들어오는 공용 규칙 한 장.

- [ ] **1단계: 파일을 쓴다**

```markdown
# 일하는 방식 (모든 프로젝트 공통)

사용자에게는 **존댓말**로 답한다. 예외 없다.

## 기본 동작
- 문제를 발견하면 **고치고 → 테스트하고 → 두 줄로 보고한다.** 허락을 기다리지 않는다.
- 두 줄이란: ① 무엇을 고쳤다 ② 무엇으로 확인했다.
- 밖으로 나가는 일(배포·공개 페이지·메일·외부 전송)만 먼저 확인받는다.

## 떠넘기지 마라
① 직접 해본다 → ② 막히면 무엇이 왜 막혔는지 명령과 응답으로 근거를 댄다 → ③ 사람만 할 수 있는 것(구글 계정 허용 클릭 등)만 부탁한다.
③에 해당한다는 증거를 못 대면 아직 ①이 안 끝난 것이다.

## 되물음은 점검 신호다
"그거 왜 안 돼?", "정말?" 은 다시 설명하라는 뜻이 아니라 **다시 확인하라는 뜻**이다. 앞서 한 말을 반복하지 않는다.

## 증거 없으면 "됐다"고 쓰지 않는다
확인한 것과 못 한 것을 그대로 적는다. 화면을 못 열었으면 "확인했다"고 쓰지 않는다.

## 세션 시작
가벼운 점검만 한다(안 올라간 커밋, 데이터가 멈췄는지, 공개 페이지가 옛 판인지). **이상 없으면 한 줄도 쓰지 않는다.** 점검하느라 대화를 다 쓰지 않는다.

## 기록
- 비밀값은 저장소에 쓰지 않는다.
- 변경은 항상 커밋·푸시한다.
- 새 사고가 나면 대화에서만 고치지 말고 해당 프로젝트의 작업 매뉴얼 "과거에 틀렸던 것" 칸에 한 줄을 더한다.

## 프로젝트 절차는 각 저장소에
배포·검증 같은 절차는 그 프로젝트의 `.claude/skills/<작업>/SKILL.md` 와 `.claude/CHECKS.md` 에 있다. 작업을 시작하기 전에 해당 파일을 먼저 읽는다.
```

- [ ] **2단계: 기억 목록 맨 위에 한 줄을 건다**

`~/claude-memory/MEMORY.md` 의 `# Memory Index` 바로 아래에 추가:

```markdown
- ⭐ [일하는 방식](일하는_방식.md) — 모든 프로젝트 공통. 작업 시작 전에 읽는다
```

- [ ] **3단계: 확인**

```bash
ls -la ~/claude-memory/일하는_방식.md && head -3 ~/claude-memory/MEMORY.md
ls ~/.claude/projects/*/memory/일하는_방식.md | head -3
```

기대: 파일이 있고, 정션으로 연결된 다른 프로젝트의 기억 폴더에서도 같은 파일이 보인다.

- [ ] **4단계: 커밋·푸시 (공용 저장소)**

```bash
git -C ~/claude-memory add -A && git -C ~/claude-memory commit -m "일하는 방식: 공용 업무 규칙 한 장" && git -C ~/claude-memory push origin main
```

### 과제 3: 작업별 매뉴얼 세 개

**파일**
- 생성: `.claude/skills/배포/SKILL.md`
- 생성: `.claude/skills/화면수정/SKILL.md`
- 생성: `.claude/skills/분배금점검/SKILL.md`

**형식:** 각 파일은 다음 다섯 칸을 갖는다 — 언제 쓰나 / 순서 / 결정 규칙 / 완료 확인 / 과거에 틀렸던 것.

- [ ] **1단계: 배포 매뉴얼을 쓴다**

내용은 현재 `CLAUDE.md` 의 "배포 절차" 다섯 단계를 그대로 옮긴다(임시 폴더 `clasp pull` → `clasp push --force` → 기존 배포 ID로 `clasp deploy -i` → `resetAllTriggers` → 재확인). "과거에 틀렸던 것" 칸에는 `--force` 누락, `-i` 누락으로 주소가 새로 생기는 것, 트리거 재설치 누락으로 3주·2일 멈춘 사건을 적는다.

- [ ] **2단계: 화면수정 매뉴얼을 쓴다**

순서: 검색으로 위치 찾기 → 수정 → 브라우저로 확인 → 커밋·푸시. 결정 규칙: 계산을 건드리면 `portfolio.html` 과 `m.html` 둘 다, 공개 페이지와 앱 화면은 일부러 다르며 같아야 하는 것은 날짜 해석 규칙(회차 판정, 예정 합의 문턱, `uncertain` 배지, `fillRakil`·`parseDay`)뿐. "과거에 틀렸던 것": 사용자는 웹 주소로 보므로 "pull 하세요"라고 시키지 않는다(한 세션에 네 번 어김), 공개 페이지 미러 누락 네 번.

- [ ] **3단계: 분배금점검 매뉴얼을 쓴다**

순서: `getDistributionAll` 로 6개사 확인 → 빈 곳이나 지난 회차를 찾으면 캐시가 아니라 파서를 본다. 결정 규칙: 두 화면이 다르면 렌더가 아니라 데이터를 먼저 의심한다. "과거에 틀렸던 것": PLUS가 6월 기사를 물고 있던 일, `clearDistCache` 가 지난 회차까지 지우던 일.

- [ ] **4단계: 확인**

배포 매뉴얼의 1단계(임시 폴더 `clasp pull`)를 실제로 한 번 해본다. 매뉴얼대로 따라가서 막히는 곳이 없어야 한다. 막히면 매뉴얼을 고친다.

- [ ] **5단계: 커밋·푸시**

```bash
git add .claude/skills && git commit -m "작업별 매뉴얼 셋: 배포·화면수정·분배금점검" && git push origin main
```
